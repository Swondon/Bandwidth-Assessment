# Documentation

## Problem 1 - Parse, Validate, and Route

`parse_alert.main` first validates the items passed in the body. It raises (`ValueError`) rather than returning an error object for every invalid-input case (payload not a dict, a missing key from `REQUIRED_FIELDS`, a `severity` outside `VALID_SEVERITIES`, or a non-int `triggered_at`) because a malformed payload is an exceptional condition, not a data value the rest of the pipeline should have to reason about. Returning `{"error": "..."}` would force every downstream branch and the notification step to special-case a second output shape, and would silently let a bad alert flow further into the system before anything noticed. Then the `dry_run` check happens before the timestamp conversion because dry_run is meant to validate the shape of the request without doing any of the work implied by actually processing it, timestamp conversion included. A dry run returns the payload untouched plus `dry_run: True`, while a real run additionally converts `triggered_at` from a Unix int to an ISO-8601 UTC string and sets `dry_run: False`. Separately, both the validation-passed message and the dry-run message are emitted with `logger.info` and a matching `print(...)`, not just the logger — in my dev Windmill instance, `logger.info` output wasn't showing up in the job's Logs panel, so the `print` is there as a way to make sure that information is actually visible when inspecting a run.

## Problem 2 - Stub a Notification Delivery

The retry logic uses a bounded 3-attempt cap with `2^(n-1)` backoff (1s after the first failure, 2s after the second) based on the project requirements. Unlike `parse_alert`, `notify_slack` does not raise when delivery ultimately fails after all 3 attempts: it returns `{"ok": False, "attempts": 3, "error": str(last_error), ...}`. A malformed alert is a bug in the input and should abort the flow immediately, but a Slack outage is an operational fact about a hypothetical downstream external system/API, and the flow (or whoever's watching it) should be able to observe and branch on that fact rather than have the whole run die. `dry_run` is handled as an early return before the retry loop even starts just like the last problem. It logs what would have been POSTed and returns `{"ok": True, "attempts": 1, "dry_run": True}` without ever invoking the Slack call, stubbed or otherwise. I built the Slack POST itself as a stub function (`_post_to_slack_stub`) with a randomized ~30% failure rate rather than a deterministic one so the retry path actually happens during testing across multiple runs instead of hardcoding specific test scenarios into the function's control flow. The message body also conditionally includes `summary` and `probable_cause` when they're present on the incoming event, so `notify_slack` works unchanged whether it's using the normal alert flow or the flow from Problem 4.

## Problem 3 - Write a CI Test

I initially wrote this test calling `parse_alert` via `wmill.run_script`, per the assessment's suggested pattern, but ran into a self-deadlock: my dev environment only has a single worker, so the test job (which blocks synchronously waiting on the child job) and the child `parse_alert` job it enqueues were both competing for that one worker slot. This meant that neither could ever run. Rather than add worker capacity, I switched to importing `main` directly from `u.ianebcondon.parse_alert` and calling it in-process as `parse_alert(...)`. This sacrifices testing the job dispatch layer, but the logic under test (validation and normalization) has no dependency on being invoked as a separate job, so an in-process call exercises exactly the same code path with none of the queuing risk. The test covers the happy path (a valid payload with `dry_run=True`, asserting `dry_run is True`, `alert_id == "ALT-4892"`, and `severity == "critical"` all pass through unchanged) and two independent invalid-input branches: the same valid payload with the `service` key stripped out (asserting the raised exception's message contains `"service"`), and the same valid payload with `severity` overwritten to the nonsense value `"banana"` (asserting the message contains `"severity"`, case-insensitively). Those are the two distinct validation checks I chose to cover, and each gets its own assertion on the exception message.

## Problem 4 — AI-Powered Incident Intelligence

Requirement 7 says no calls should reach the LLM provider when `dry_run` is set, but the worked Expected Output example shows a fully-classified result under `dry_run: true`, which isn't literally achievable without calling the model. I took the requirements literally. This means that in `dry_run` mode, `classify_alert` skips `_classify_with_llm` entirely and returns a pre-made `_DRY_RUN_STUB` classification matching the worked example (`payments-api` / `critical` / a Redis-pool-exhaustion message, summary, and probable cause), and the real OpenAI call only happens when `dry_run=False`. This means the entire flow, including the AI step, can be exercised end-to-end (and eventually tested in CI) without spending API credits or depending on network access, at the cost of the dry-run path not actually validating the LLM integration itself. Right now this path is treated as a "surpress any external API calls path". For the model, I picked `gpt-4.1-mini` over a larger model because pulling a service name and severity out of a log line, and writing one-sentence summary/probable-cause text is short-context classification and light summarization. It is not multi-step reasoning, so the mini tier is materially cheaper with no real capability gap for this use case. I used `client.responses.parse` with a Pydantic `AlertClassification` model as `text_format` so the response is schema-enforced rather than hand-parsed JSON. The API key itself comes from a Windmill resource variable (`wmill.get_variable`) rather than being passed in or hardcoded. I still validate the model's `severity` output against the same `VALID_SEVERITIES` set used in `parse_alert` because responses are coming from an external API. Because `classify_alert` can be the first script the flow calls, it does its own `triggered_at` conversion rather than assuming `parse_alert` already did it.
